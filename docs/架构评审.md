# 软件架构评审与优化方案

> 评审时间：2026-11-06　范围：`backend/`（Python 采集发送端）、`cloudflare/`（Cloudflare 订阅与发布端）、
> `.github/workflows/`、`config/`、`backend/prompts/`、`data/`
> 结论基于当时代码与运行记录，不含预测性论断。

---

## 0. 结论摘要

系统**功能完整、运行时边界清晰**：Python 负责采集/分析/发信，Worker 负责账号/偏好/发布物，
两者只通过 3 个 HTTP 契约 + 2 枚同值密钥耦合。这个切分是对的，不需要推倒重来。

但演进速度已经把三笔结构性欠账放大到会引发事故的程度：

1. **状态层是「六个 JSON 文件 + 每次 git commit 回写」**——并发写会互相覆盖、历史被状态污染、
   仓库里躺着 572 KB 的 `ai.json`；
2. **编排层是一个 574 行、17 阶段的单函数 `main()`**——65 个分支、15 个 `return`，
   阶段之间靠副作用顺序耦合，无法单独测试"只跑变更检测"；
3. **领域词汇在多处复制**——同一套分类/角色/赛事在各端出现 3–6 次，
   跨端一致性一度靠「Python 解析 TypeScript 源码文本」来保证。

评分（相对本项目应有的水准，非行业绝对分）：

| 维度 | 现状 | 主要短板 |
|---|---|---|
| 边界与分层 | ★★★★☆ | 两个运行时切分合理，HTTP 契约清晰 |
| 契约一致性 | ★★★☆☆ | 赛事已收敛，分类/角色/payload 仍多处重复 |
| 状态一致性 | ★★☆☆☆ | 文件即数据库、git 即持久化、无并发保护 |
| 可测试性 | ★★☆☆☆ | 自研断言脚本，无阶段级集成测试，无固定时钟 |
| 可观测性 | ★★★☆☆ | 有失败告警与心跳，缺运行级指标 |
| 可演进性 | ★★☆☆☆ | `main()` 巨石 + 隐式全局状态 |

## 1. 现状架构

### 1.1 三条链路

```
① 采集链（GitHub Actions，每天 10:00 / 20:00 两轮）
   cron/dispatch → yds.main
     → sources(fetch 调度：线程池 + 同 URL 合并 + per-host 限流)
     → state 变更检测 → 详情抓取 → AI 分析（backend/prompts/ + backend/ai/）
     → dispatch（即时 / 日报 / 周报 / 紧急）→ Resend / SMTP

② 发布链（同一进程内，发信之后）
   build_payload → POST /api/notices → KV `feed:notices`
     → /archive（服务端渲染）、/feed.xml、/calendar.ics（签名个人日历）

③ 订阅链（Worker）
   /api/login → 邮箱验证码 → KV user:/sub:/session: → /dashboard 偏好
     ↑ Python 每轮 GET /api/list 拉取订阅者与偏好
```

### 1.2 运行状态分布

| 载体 | 内容 | 谁写 | 谁读 |
|---|---|---|---|
| `data/seen.json` | 已推送记录、列表/详情指纹、发布指纹 | Actions | Actions |
| `data/ai.json` | AI 分析结果 + 公告正文（≤3 KB/条） | Actions | Actions |
| `data/pending.json` | 日报/周报待发池 | Actions | Actions |
| `data/schedule.json` | 官方赛程（19 项） | Actions（每周） | Actions + Worker |
| `data/reminders.json` | 已发日程提醒 | Actions | Actions |
| `data/zones.json` | 专区轮询游标 / 全量扫描日期 | Actions | Actions |
| KV `feed:notices` | 归档 / RSS / 日历的只读数据集 | Actions | Worker |
| KV `user:/sub:/session:/confirm:` | 账号与偏好 | Worker | Worker + Actions |

这八个载体里，**前六个都是「进程内状态」，靠 git 提交在两次 Action 之间传递**——这是全系统最脆弱的一环。

## 2. 问题清单

按「会不会引发事故」排序，不按代码美观度。

### A1　状态层：六个 JSON 当数据库，git 当持久化【严重】

**证据**
- `data/` 下 6 个状态文件，共约 590 KB；`ai.json` 单文件 572 KB（230 条分析 + 正文缓存）。
- `.github/workflows/notify.yml` 的「保存状态」步骤：`git pull --rebase --autostash` + `git push`，
  失败重试 3 次，仍失败则 `exit 1`。
- 实际已发生故障：本地提交与 CI bot 的状态提交分叉，`git pull` 报 divergent branches。

**影响**
1. **并发覆盖**：CI 内有 `concurrency: yds-notify` 串行化，但本地 `--backfill` 与 cron 同时跑
   会各写一份 `seen.json`，后写者覆盖前者 → `seen` 回退 → **下一轮重复发信**。
2. **提交即副作用**：内容一变就产生一次 bot commit（已有 4 次），
   每次都要 rebase，冲突是常态而非意外。
3. **体积无界**：`keep=800` × 每条 3 KB 正文 ≈ 2.4 MB 上限，且永久留在 git 历史里。
4. **不可查询**：「某赛事最近 30 天推了什么」只能全量加载 + 遍历，无法下推过滤。

**根因**：没有状态访问层，`State` / `AiCache` / `ScheduleStore` 各自 `open/json.load`，
持久化策略（文件 + git）与领域语义（"发过没有"）焊死在一起。

---

### A2　编排层：`main()` 是 574 行 / 17 阶段 / 65 分支 / 15 个 `return`【严重】

**证据**：`backend/main.py:166-571`。阶段依次为：读配置 → 拉名单 → 决定抓取范围 →
列表抓取 → 推进专区游标 → 赛程刷新 → 加载状态 → 变更检测 → 决定抽检 → 详情抓取 →
AI 分析 → 归档同步 → 汇总裁剪（基线/追赶）→ 预览 / dry-run → 调度发信 → 记账 → 状态保存。

**影响**
- 无法单独验证某一阶段：想测「变更检测 + 追赶裁剪」必须跑通整条链（含网络）。
- **副作用顺序危险**：专区游标在「列表抓取成功后、发信之前」推进（`main.py:261-266`）。
  若后续阶段崩溃，游标已前进，这批赛事要等下次全量扫描才回头。
- 退出码语义分散：`1`（抓取失败）、`2`（配置/状态问题）在 15 个 `return` 里各写一遍。
- 四个开关（`--check/--dry-run/--preview/--backfill`）以 `if` 形式渗透进 15 处业务逻辑，
  新增一种运行模式要改 5 个以上位置。

---

### A3　契约：同一份领域词汇出现在 3–6 处，跨端曾经靠「解析源码」对齐【高】

**证据**
- 分类（报名参赛/评审与名单/决赛与收官/赛事动态/其他通知）：
  `backend/models.py:19` `VALID_CATEGORIES`、`backend/ai/schema.py:19`、`backend/mailer.py:27` `CATEGORY_ORDER`、
  `backend/recipients.py:31` `CATEGORY_TO_KEY`、`cloudflare/src/auth.ts` `CATEGORIES`、
  `cloudflare/src/handlers/feed.ts` `AI_CATEGORIES`。
- 角色（student/advisor/admin/organizer）：`backend/personas.py`、`backend/recipients.py`、
  `auth.ts`、`feed.ts` 各一份。
- 赛事（20 项）：**本轮已收敛**（见 §5）。

**影响**：新增一个分类要改 6 处，漏一处就出现「邮件里有、归档里没有」或「后台勾了不生效」这类
难以复现的错位；契约测试是"事后对齐"，不是"编译期/运行期强制"。

---

### A4　Worker：handler 直连 KV，没有读模型【中】

**证据**：`handlers/feed.ts` 639 行，`loadFeed()` 每次请求把整块 `feed:notices`
（最多 300 条）解析 + `normalizeNotice` 全量归一化；isolate 60 s 缓存只能缓解。

**影响**
- 请求成本随通知数线性增长（当前 200 条约 100 KB / 次），日历客户端 15 分钟轮询时是纯浪费。
- 换存储（D1/R2）或加索引要改 handler，而非只换适配器。
- 发布时只能整块覆盖写，单 key 成为全局串行点。

---

### A5　抓取层：猴子补丁 + 模块级全局统计【中】

`enrich_only()` 直接替换数据源实例方法（`main.py:152-163`，被迫 `# type: ignore`），
`fetch.STATS` 是模块级全局，`reset_stats()` 靠调用方自觉。

**影响**：隐式状态使测试相互污染；数据源实例变成"有状态对象"，同一实例不能被两轮复用。

---

### A6　时间：「今天」是隐式全局【中】

`date.today()`（main / schedule）、`datetime.now()`（dispatch 摘要窗口）直接读系统时间，
正确性依赖 CI 里的 `TZ=Asia/Shanghai`。本地或换环境跑，"日界线"会平移 8 小时。

**影响**：摘要窗口、`push_max_age_days`、赛程 T-N 提醒、暂停到期判断全部受此影响，且无法用测试固定。

---

### A7　去重键用标题，跨赛事会互相吃掉【潜在，实测暂未发生】

`main.collect()`：`deduped.setdefault(re.sub(r"\s+", "", item.title), item)` 对所有来源、
所有赛事生效。19 项赛事大量使用模板标题（「关于举办…的通知」「大赛通知」「赛程一览」），
一旦不同赛事出现同名标题，只保留一条，另一条**从归档与邮件里彻底消失**。

**实测**：当前 82 条列表页条目中同标题组为 0，跨赛事同标题组为 0——所以现在没有丢数据。
但这是"运气好"而不是"设计安全"：赛事扩到 20 项、每项都有「赛程一览」时，碰撞是时间问题。

**建议（不紧急）**：去重键改为 `(contest, 规范化标题)`，并保留"同 URL"判据用于跨栏目转载；
全站级通知 `contest` 为空，单独一档。

---

### A8　新增数据源成本高，且没有「解析健康度」信号【中】

新增一项赛事要动 3 处：`config/contests.json`、`sources.py` 注册、`config/config.yaml`。
DOM 改版的唯一信号是"列表页 0 条"（整体红），单个栏目解析退化为 0 却静默。

**建议**：把选择器下沉为声明式配置，`BaseSource` 提供通用列表解析器；
每个源记录"本页解析条数"，连续 N 轮为 0 时告警（而不是等整体归零）。

---

### A9　可观测性：有告警和心跳，缺运行级指标【中】

已有：失败即告警的 `alert` job、`HEARTBEAT_URL` 死信箱、`fetch.stats_line()`。
缺：每轮的 runId、各阶段耗时、AI 调用数/失败数、发送条数、KV 写入次数——
排查"今天为什么没收到邮件"目前只能翻整份 Actions 日志。

**建议**：每轮输出一行结构化摘要（JSON 日志）+ 落 `data/run.json` 供归档页/状态页展示。

---

### A10　配置面：42 个环境变量 × 3 个存放位置，无 schema 校验【低-中】

`.env`（本地）/ GitHub Secrets（CI）/ Cloudflare Variables（Worker）三处人工同步，
`_s()` 对拼写错误静默返回空串并走默认值。已有 `mail_preflight()`，但只覆盖发信。

**建议**：扩展为全量启动自检，打印"生效配置（密钥脱敏）+ 缺失项"，配置错误在启动时红。

## 3. 目标架构

### 3.1 四条原则

1. **单一状态边界**：领域代码不知道状态存在哪里，只面向 `StateStore` 协议；
   文件后端只是其中一种实现。
2. **契约先行**：所有跨端共享的词汇与 payload 都有机器可校验的定义文件，代码不再各写一份。
3. **纯函数领域层**：推断、过滤、去重、归一化、日历展开都是纯函数，副作用集中在适配器。
4. **编排与副作用分离**：一次运行 = 一串 stage，每个 stage 显式声明依赖与产物，
   失败可停可续，退出码集中映射。

### 3.2 Python 端目标结构

```
backend/
  cli.py            # argparse / 退出码映射（唯一入口）
  pipeline.py       # RunContext + stage 编排；main() 目标 < 80 行
  stages/
    detect.py       # 列表抓取 + 变更检测（纯输入输出，可单测）
    detail.py       # 详情抓取 + 每日抽检
    analyze.py      # AI 分析（含降级）
    publish.py      # 归档同步（内容指纹）
    notify.py       # 汇总裁剪 + 调度发信 + 记账
  domain/           # 纯函数：personas / schedule 展开 / 去重键 / 日期抽取
  store/
    base.py         # StateStore 协议：seen / ai / schedule / reminders / zones
    files.py        # 现有 JSON 实现（过渡，行为等价）
  adapters/         # fetch / senders / kv（HTTP）
```

### 3.3 Worker 端目标结构

```
cloudflare/src/
  domain/           # 纯函数：normalizeNotice / filterPrefs / calendar 展开
  ports/            # Repo 接口：Users / Sessions / Feed / Stats
  adapters/kv.ts    # KV 实现（未来换 D1/R2 只改这里）
  handlers/         # 薄层：解析请求 → 调用 use case → 渲染
  # 页面渲染已拆到 frontend/（archive/* 结构与样式分离）
```

### 3.4 契约层（跨端）

```
config/
  contests.json         # ✅ 已落地
  enums.json            # ⬜ 分类 / 角色 / 阶段 / 频率（各端只读不写）
  notice.schema.json    # ⬜ /api/notices payload 的 JSON Schema
  validate.py           # ⬜ 本地与 CI 校验：Python 产物 vs schema
```

## 5. 本轮已落地的两项优化

### 5.1 赛事契约收敛（A3）

**改了什么**

| 文件 | 变更 |
|---|---|
| `config/contests.json` | 新增：20 项赛事的唯一事实源（名称 + 研创网专区 id） |
| `backend/personas.py` | 删除硬编码的 `CONTESTS` 与 `CONTEST_IDS`，改为加载契约（运行时读文件） |
| `cloudflare/src/auth.ts` | 删除 20 行硬编码清单，改为 `import CONTRACT from "../../config/contests.json"`（构建期内联） |
| `cloudflare/tsconfig.json` | 开启 `resolveJsonModule`，把 `../config/*.json` 纳入 include |
| `backend/selftest.py` | 删除「解析 auth.ts 源码文本比对」的断言，改为验证两端都读契约 + id 映射一致 |

**为什么这算架构优化而不是重构洁癖**

旧做法是：Python 里一份、TypeScript 里一份，测试去读 TS 源码、按 `// <contests>` 标记截取数组、
正则抠出字符串再比对。这是**用测试弥补设计缺陷**——两端都能改漏，测试只能在事后喊，
且一旦 TS 换个写法（比如 `as const`、换行、注释）测试就假失败。

新做法是同一份数据被两个运行时消费：Python 运行时读、Worker 构建期打包。
契约从"靠人记 + 靠测试追"变成"物理上只有一份"。

### 5.2 单实例运行锁（A1 的最危险失效路径）

新增 `backend/lock.py`：`fcntl.flock` 非阻塞独占锁，包住所有会**读-改-写状态**的运行模式
（定时任务、`--backfill`）；`--check` / `--dry-run` / `--preview` 是只读的，不取锁。

- 锁文件 `data/.run.lock` 只记 pid，进程退出（含崩溃 / 被 kill）由内核自动释放，
  不存在"死锁文件"需要人工清理；
- 第二个实例立即以退出码 `2` 结束并给出明确原因，不再出现"两个进程各写一份 seen.json"；
- 锁文件已进 `.gitignore`，CI 的干净 checkout 也不受影响。

这是对 A1 的**止血**而不是根治：根治要等 P1-2 的 `StateStore` 与 P2-1 的状态外置。

### 5.3 状态外置到 R2（A1 的根治）

新增 `backend/store/r2.py` + `backend/store/__init__.py`：把 `data/*.json` 从「git 提交」
改为「对象存储读写」，Actions 仍是执行者，**调度方式完全没动**。

| 维度 | 改造前 | 改造后 |
|---|---|---|
| 传输方式 | `git commit` + `pull --rebase`（3 次重试） | `GET` / `PUT` 一个对象 |
| 并发保护 | CI concurrency + 本地 flock | 追加 `If-Match` 条件写，跨机器也有效 |
| 体积 | `ai.json` 572 KB | gzip 后约 166 KB（省 71%） |
| 仓库 | 每轮可能产生 bot commit，冲突是常态 | 仓库里不再出现状态提交 |
| 权限 | 需要 `contents: write` | 可去掉（状态不走 git） |
| 计费 | 无 | R2 免费额度内（每天约 4 次写操作） |

设计上的三个关键点：

1. **业务代码零改动**：本地仍是普通 JSON，`pull` 在运行前把对象落盘、`push` 在退出时上传，
   上层感知不到对象存储；
2. **写回放在 `atexit`**：`main()` 有十几个 `return` 分支（基线、追赶、无新内容、只有提醒……），
   逐个补 `push` 迟早漏一个，漏掉就意味着下一轮重复发信；
3. **冲突不覆盖**：远端 ETag 已变化时抛 `StateConflict`，只记 error 并保留远端版本 ——
   宁可这轮状态滞后，也不能把对方刚写的「已推送」标记冲掉。

未配置 R2 时 `build_store()` 返回 `None`，整条链路退回旧行为，**零风险升级**。

**验证**：Python 自测 210 项（新增 12 项对象存储用例：gzip、未变跳过、ETag 冲突检测、
冲突抛错、缺配置不启用），REST 客户端按 `STATE_BACKEND` / 账户级 Token 自动启用或降级。

**验证**：Python 自测 198 项（新增 3 项锁用例）、Worker 端到端 259 项全过，
`tsc` 干净，bundle 104.8 KB，`python -m backend --check` 正常跑通。

## 6. 刻意不做的事

| 方案 | 为什么不做 |
|---|---|
| 引入 Postgres / Supabase 存订阅者 | 当前 3 个订阅者，运维成本远大于收益；KV 的读写模式与访问量匹配 |
| 把 Python 搬上 Worker | 抓取 + 解析 + 多赛事并发 + 邮件渲染需要 Python 生态与分钟级运行时 |
| 拆成微服务 | 两个运行时已是合理切分；再拆只会增加契约数量 |
| 给每个数据源写单测 | DOM 解析的性价比低于"解析条数健康度"监控，后者能覆盖改版 |
