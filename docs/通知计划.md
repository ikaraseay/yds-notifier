# 研电赛通知计划（人员视角版）

> 目标：把「等官网发新通知」变成「按赛事阶段主动提醒」。
> 官网一年只发几十条通知，且 70% 是倒计时 / 回顾；只做「新公告推送」必然又少又吵。
> 本方案用**确定性赛程数据**补足信息密度，再用**人员视角**决定谁该看什么。

---

## 一、数据覆盖现状

| 维度 | 当前覆盖 |
|---|---|
| 常规栏目 | 研电赛专区、大赛通知、大赛新闻、大赛文件、中国电子学会通知公告 |
| 赛事专区 | 19 个可扫专区（20 项赛事中 1 项无独立专区） |
| 官方赛程 | 19 项赛事的报名 / 提交 / 决赛时间节点，写入日历与提醒 |
| 事件日期 | AI 从公告正文抽取并缓存在 `data/ai.json`；未启用 AI 时按确定性规则推断 |
| 抓取节奏 | 每天 10:00 / 20:00 两轮；进行中的赛事每轮扫，已结束的每 14 天扫一次 |

信息密度来自三条互补来源：列表页的新通知、结构化赛程表、公告正文里的真实事件日期。

## 三、人员视角：谁在什么时候需要什么

### 3.1 四类人

| 视角 | 典型角色 | 核心诉求 | 不该打扰的内容 |
|---|---|---|---|
| `student` 参赛学生 | 队长、队员 | 报名、赛题、提交、答辩、获奖、报销 | 承办征集、资格审核细则 |
| `advisor` 指导教师 | 导师、带队老师 | 组队规则、评审安排、决赛行程、证书 | 承办征集、缴费对账 |
| `admin` 培养单位 | 研究生院、学院管理员 | 资格审核、缴费统计、获奖名单、承办申报 | 赛题细节、企业命题宣传 |
| `organizer` 分赛区 / 承办方 | 赛区秘书处、承办高校 | 分赛区资讯、承办征集、赛程协调 | 学生报名操作细节 |

### 3.2 阶段 × 视角矩阵

| 阶段 | 学生 | 导师 | 培养单位 | 赛区/承办 | 典型通知 |
|---|---|---|---|---|---|
| 报名 | ● | ● | ○ | — | 报名开启/截止、赛题发布、章程 |
| 资格审查 | ○ | — | ● | — | 资格审核、材料补交 |
| 缴费 | ○ | ○ | ● | — | 报名费、会务费、对账 |
| 提交作品 | ● | ● | — | — | 作品上传、材料提交截止 |
| 评审 | ● | ● | ○ | — | 初审、答辩、复核 |
| 决赛 | ● | ● | ○ | ○ | 决赛日程、报到、颁奖 |
| 公示 | ● | ● | ● | — | 名单公示、成绩公布 |
| 获奖 | ● | ● | ● | — | 获奖名单、证书下载 |
| 报销 | ● | ● | ● | — | 报销文件、发票、票据 |
| 承办 | — | — | ● | ● | 承办征集、申办、组委会 |
| 动态 | ● | ● | — | — | 倒计时、开幕/落幕、企业合作 |

> ● 主要关注　○ 次要关注　— 默认不推送

### 3.3 通知分层

| 层级 | 触发条件 | 送达方式 | 频率 |
|---|---|---|---|
| 紧急快报 | AI `critical`，或规则识别「7 天内截止」且阶段属于报名/提交/缴费/资格审查 | 立即发信，不进摘要池 | 事件驱动 |
| 日程提醒 | 官方赛程的截止日命中 T-30 / T-7 / T-3 / T-1 | 独立一封「日程提醒」 | 每档一次 |
| 新通知 | 列表页出现新条目 / 官网修订同一篇 | 即时或进摘要池 | 每天 10:00 / 20:00 探测 |
| 日报 / 周报 | 用户选择 daily / weekly | 每天 10:00 / 周一 10:00 汇总 | 固定 |
| 归档 / RSS / 日历 | 全部公开通知 + 官方赛程 | 网页订阅 | 实时同步 |

### 3.4 降噪规则

1. **倒计时折叠**：标题含「倒计时 / 圆满 / 落幕 / 回顾 / 花絮」→ `stage=动态`、`is_low_value=true`，
   摘要邮件里折叠成一行，不进紧急通道。
2. **同标题去重**：同一内容同时出现在「大赛通知」和「大赛文件」时按标题去重，保留附件更全的一条。
3. **历史条目拦截**：超过 `push_max_age_days`（默认 14 天）的「新条目」只归档、不推送
   （仍标记已读，历史从 `seen.json` 重建，归档 / RSS / 日历不受影响），
   避免首次接入赛事专区时把上年度名单当新闻群发。
4. **同天截止合并**：报名与提交同一天截止时，只发一条「报名截止」提醒。
5. **追赶模式**：单轮新增超过 `catchup_threshold`（默认 10）条时，只推最近
   `catchup_size`（默认 8）条，其余静默归档——仍能在归档页 / 日历看到，
   但不会连发多封大邮件。扩充数据源或长时间停摆后尤其重要。
6. **人员视角过滤**：收件人配置了 `audiences` 时，只收命中视角的通知；未配置则收全量。

### 3.5 后台设置（订阅者视角）

控制台 `/` 分为五块，改动即时保存到 `/api/prefs`：

1. **我的角色**：学生 / 导师 / 培养单位 / 赛区承办，多选按并集；
2. **关注的赛事**：20 项赛事复选（含 EDA 专项），提供「只选研电赛 / 全选 / 清空」；
   一个都不选 = 接收全部赛事；
3. **通知栏目**：报名参赛 / 评审与名单 / 决赛与收官 / 赛事动态；
4. **推送频率**：即时 / 日报 / 周报；
5. **暂停订阅**：暂停到指定日期。

筛选逻辑是三层交集：**栏目 × 角色 × 赛事**。全站级通知（赛程一览等）赛事为空，
不会被赛事筛选误伤。

### 3.6 角色版邮件

- 订阅者只勾选**一个角色** → 发该角色专版：
  - 主题前缀 `〔参赛学生〕`；
  - 顶部「按赛事汇总」：每项赛事的条数、最近时间节点、**该赛事的日历 / 列表链接**；
  - 正文按赛事分组，每组标题右侧带「赛事日历 / 赛事列表」。
- 勾选**多个角色** → 发综合版：顶部按角色分组，只列出收件人勾选的角色，
  同一通知可出现在它适用的所有已勾选角色下；同时也有「按赛事汇总」。
- 赛事链接形如 `/calendar.ics?email=…&token=…&contest=电子设计竞赛&audience=student` 与
  `/archive?contest=电子设计竞赛`，订阅者可以只订自己关注的赛事日历。
  日历链接必须带签名（无签名返回 401）。



## 四、邮件结构（读者实际看到什么）

综合版邮件从上到下：

1. **按角色分组**：只出现收件人勾选的角色（一个都没勾 = 不限制才显示全部），
   组标题就是角色名，每条给出「阶段 + 标题 + 一句话动作」，最多 3 条。
2. **按赛事汇总**：每项赛事的条数、最近节点、赛事日历 / 列表链接。
3. **按分类分组的通知卡片**：日期、阶段徽标、赛事名、面向人群、AI 摘要、
   动作高亮条、事件日期、附件。
4. **退订 / 项目主页 / 研电赛官网**。

时间节点已全部过去的通知不进邮件（含本轮才抓到的旧公告），只留在归档里。

视角专用版（配置了 `personas[].mail_to`）：
标题下标注「本版面向：参赛学生」，只包含命中该视角的通知。

## 四·一、归档页（网页端）

`/archive` 是一条独立整页设计（Memphis 风格），结构与样式分离：

| 文件 | 职责 |
|---|---|
| `worker/src/ui/archive/page.ts` | 筛选 → 统计 → 视图 → 外壳 的组装 |
| `worker/src/ui/archive/list.ts` | 通知卡片：阶段 / 赛事 / 摘要 / 日程 / 行动 / 面向 |
| `worker/src/ui/archive/calendar.ts` | 日历视图与「按天日程」 |
| `worker/src/ui/archive/common.ts` | URL 改写（筛选条件跨视图保留）、chip、开关、日期工具 |
| `worker/src/ui/archive/layout.ts` | `<html>` 外壳 + CSP nonce |
| `worker/src/ui/archive/styles.css` | 全部样式；esbuild `--loader:.css=text` 内联为字符串 |

判定逻辑（`worker/src/handlers/feed.ts`）只剩取数与转交，改版式不碰后端。

### 日历视图的三个体验点

1. **格子里带来源**：每格最多 3 条节点，写作「节点名 + 来源小字」，
   例：`报名截止 研创网`、`报名截止 电子设计竞赛`（后者来自官方赛程）。
   右上角数字是当天节点总数；格子在 620px 以下隐藏小字，只留日期与数字。
2. **点格子定位当天**：格子是锚点链接 `#d-YYYY-MM-DD`，跳到下方「按天日程」
   对应分组，`:target` 会高亮该组；分组标题本身也是锚点，便于复制分享。
   每个节点标题链回公告原文或官方赛程页。
3. **月份快切**：`‹ 上月 / 下月 › / 本月` + `<details>` 折叠的「年 + 12 个月」
   网格（有日程的月份标蓝）。全部是链接，不需要 JS（站点 CSP 不允许脚本），
   且翻月会保留当前的赛事 / 分类 / 角色筛选。

**只收真实日期**：日历节点来自 AI 抽出的 `aiEvents`，或确定性规则抽到的 `deadline`；
**绝不回落到发布日期**。否则每条普通动态都会在发布当天占一个格子，
既复刻了「日历只显示发布日期」的老问题，也会把月历糊满。
列表视图仍然完整展示这些动态，只是它们不占日历。

## 六、AI 开启后的增强（提示词 v2）

| 能力 | 规则降级（无 Key） | AI 增强（有 Key） |
|---|---|---|
| 赛事名 | 标题别名匹配，识别不出默认研电赛 | 语义判断，含多项赛事时留空 |
| 阶段 | 关键词表 + 回顾类前置判定 | 结合正文判断，处理「延期」「补充通知」等隐含阶段 |
| 人群 | 阶段映射 + 标题点名（培养单位/导师/赛区） | 结合正文判断真实受众 |
| 要做什么 | 阶段模板句 | 结合截止日与材料要求生成具体动作 |
| 事件日期 | 双向窗口正则 + 合理性校验 | 语义抽取，支持「报到」「公示期」「证书申领」等 |
| 紧急度 | 7 天内截止 + 延期关键词 | 综合判断变更、影响面 |

AI 结果按内容指纹缓存在 `data/ai.json`，无新内容时零调用；
提示词升版（`prompts/manifest.yaml`）会让缓存全量失效并重算。

## 七、抓取压力与日历个性化

### 抓取：快，但不给官网加压

单轮要访问 13 个列表页 + 若干详情页。优化前后实测（同一网络、同一数据源）：

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 单轮耗时 | 37.6s | 15.3s |
| HTTP 请求数 | 40 次 | 26 次 |
| 同 URL 重复请求 | 14 次 | 0（进程内合并） |
| 单主机并发 | 1（串行） | ≤ 2（信号量） |

做法：

1. **两阶段抓取**：先只抓列表页判断有无变化，命中才抓详情——这是最大的省流手段。
2. **线程池并发**：列表页与详情页并行，`YDS_WORKERS` 默认 6。
3. **同 URL single-flight**：研电赛专区与专区轮询会命中同一个列表页地址，
   同一轮只真正请求一次，其余线程等待复用。
4. **每主机信号量**：`cpipc.acge.org.cn` 最多 2 个在途请求。
5. **每日详情抽检限额**：`full_check_limit: 12`，按「上次复核日期」轮转，
   一圈覆盖全部 30 天内发布的条目，而不是天天重复同一批最近通知。
6. **每天两轮扫描**（`config.yaml.contest_status`，默认开启）：上午轮扫全部源，
   晚上轮只扫高变化源（`runs: twice`）与进行中的赛事专区；AI 判定为「已结束」的
   赛事默认每 14 天扫一次。稳态下上午轮约 17 次请求、晚上轮约 12 次（含 robots 探测），
   合计约 29 次/天。
   判定每 14 天用一次 AI 批量复核（约每两周 1 次 API 调用），结果缓存 `data/zones.json`。
   `ended_scan_days` 与 `push_max_age_days` 同为 14 天，避免复扫发现的通知超龄只归档。
   官方赛程或通知仍有未来节点 → 代码强制判为进行中；官方赛程缺该赛事节点、
   AI 不可用 / 判定失败 → 全部按进行中处理，宁可多扫也不漏通知。
   订阅者都限定了关注赛事时只扫这些赛事，请求数进一步下降。

日志会输出 `HTTP 请求 N 次（同 URL 复用 M 次，重试 X 次，失败 Y 次）`，异常可直接定位。

### 日历：只对本人签发

`/calendar.ics` 只认签名链接：

```
https://<域名>/calendar.ics?email=you@example.com&token=<exp>.<sig>
```

- 没有签名、签名不对、token 过期、用途不符 → 一律 `401`，页面提示去控制台领取；
- 签名域是 `cal`，与退订的 `unsub` 互不通用；日历链接泄漏也无法退订；
- Worker 校验签名 → 读该用户 KV 里的偏好 → 只输出**其关注赛事 × 其角色**的事件；
  全站级通知（无赛事归属）不会被赛事筛选误伤；
- 赛程事件按赛事收敛，角色不影响赛程（赛程本身没有角色属性）；
- 控制台「我的日历」可一键复制地址；邮件页脚也有同一个入口；
- 响应头是 `Cache-Control: private, max-age=300` + `X-Robots-Tag: noindex`，
  不允许中间代理共享缓存，避免日程串人。

### KV 压力与偏好保存

通知与赛程存在同一条 KV 记录里，一次读取即可；isolate 内 60 秒缓存，写入时主动失效，
边缘读取使用 KV `cacheTtl: 60`。无签名的日历请求直接 401，不读 KV。
免费额度为每天 10 万次读 / 1,000 写 / 1,000 删（与发布链路共用）。

偏好保存是 **2 写 + 1 删**（`user:`、`sub:`，并删除 `subs:index` 让 `/api/list` 重建）。
前端做了两层合并：

- **5 分钟暂存窗口**：改动先写 `localStorage`，最后一次操作后 5 分钟才提交；
