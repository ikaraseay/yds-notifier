# 研电赛通知计划（人员视角版）

> 目标：把「等官网发新通知」变成「按赛事阶段主动提醒」。
> 官网一年只发几十条通知，且 70% 是倒计时 / 回顾；只做「新公告推送」必然又少又吵。
> 本方案用**确定性赛程数据**补足信息密度，再用**人员视角**决定谁该看什么。

---

## 一、诊断：为什么之前「检测到的信息太少」

改造前实测（2026-11-06）：

| 指标 | 改造前 | 改造后 |
|---|---|---|
| 列表页条目 | 20 条 | 52 条（已按标题去重） |
| 覆盖栏目 | 研电赛专区 1 个 | 研电赛专区 + 大赛通知 + 大赛新闻 + 大赛文件 + 电子学会 |
| 覆盖赛事 | 1 项（电子设计竞赛） | 19 项主题赛事的赛程 |
| 有效信息 | 6 条（14 条是「倒计时 N 天」） | 6 条通知 + 19 项赛程 + 19 项赛事的 57 个时间节点 |
| 中国电子学会 | 2 页 20 条，命中 0 条 | 保留兜底，扩关键词 |

根因不是「抓取频率低」，而是三点：

1. **只抓了一个栏目**：研创网还有全站级「大赛通知 / 大赛新闻 / 大赛文件」，之前完全没抓。
2. **只覆盖一项赛事**：页脚列出 19 项主题赛事 + 1 项专项赛，用户可能同时关注创"芯"、AI、机器人。
3. **没有利用赛程表**：官方《各主题赛事赛程一览》是一张结构化表格，含 19 项赛事的
   报名 / 提交作品 / 决赛时间，是全年最有价值、最稳定的信息，之前完全没解析。

## 二、数据源覆盖（对应官网页脚菜单）

### 2.1 主题赛事（19 项 + 1 项专项赛）

| 分组 | 赛事 | 当前覆盖方式 |
|---|---|---|
| 电子信息核心 | 电子设计竞赛（研电赛） | 专区通知 + 赛程 + 日历 |
| 集成电路 | 创"芯"大赛、EDA 精英挑战赛 | 大赛通知 / 新闻 + 赛程 |
| 智能技术 | 人工智能、机器人、智能建造、操作系统开源 | 大赛通知 / 新闻 + 赛程 |
| 交叉学科 | 数学建模、能源装备、网络安全、"双碳"、金融科技 | 大赛通知 / 新闻 + 赛程 |
| 人文社科 | 公共管理案例、乡村振兴、企业管理、"文化中国"、国际中文教育、"美丽中国"、智慧城市、未来飞行器 | 大赛通知 / 新闻 + 赛程 |

> 说明：除研电赛外，其余赛事的**独立专区通知**暂未逐个抓取（19 个栏目的 DOM 差异大、
> 维护成本高）。它们通过「大赛通知 / 大赛新闻 + 官方赛程」覆盖关键节点，
> 需要深挖某一赛事时，只需在 `config.yaml` 增加一条 `key: cpipc, contest: <id>`。

### 2.2 资讯栏目

| 栏目 | 地址 | 价值 | 抓取策略 |
|---|---|---|---|
| 研电赛专区通知 | `/cw/contestNews/list/6/{page}` | 最高 | 3 页，每轮 |
| 各赛事独立专区 | `/cw/contestNews/list/{contestId}/{page}` | 高（其他 18 项赛事） | 1 页；关注赛事优先，其余每轮 4 项轮询 |
| 大赛通知 | `/pw/notice/list/{page}` | 高（赛程一览、年度启动、暂停举办） | 2 页，每轮 |
| 大赛新闻 | `/pw/news/list/{page}` | 中（赛事动态） | 1 页，低优先级 |
| 大赛文件 | `/pw/document/list/{page}` | 中（章程、申报书、年度报告） | 1 页 |
| 中国电子学会通知 | `/list_43/` | 低（全学科混排） | 2 页 + 关键词过滤 |

> 赛事专区 id 见 `yds/personas.py` 的 `CONTEST_IDS`。订阅者在后台勾选赛事后，
> 只抓勾选的；无人限制时按 `data/zones.json` 的游标每轮抓 4 项，约 1 小时覆盖全部。

## 三、人员视角：谁在什么时候需要什么

### 3.1 四类人

| 视角 | 典型角色 | 核心诉求 | 不该打扰的内容 |
|---|---|---|---|
| `student` 参赛学生 | 队长、队员 | 报名、赛题、提交、答辩、获奖、报销 | 承办征集、资格审核细则 |
| `advisor` 指导教师 | 导师、带队老师 | 组队规则、评审安排、决赛行程、证书 | 承办征集、缴费对账 |
| `admin` 培养单位 | 研究生院、学院管理员 | 资格审核、缴费统计、获奖名单、承办申报 | 赛题细节、企业命题宣传 |
| `organizer` 分赛区 / 承办方 | 赛区秘书处、承办高校 | 分赛区资讯、承办征集、赛程协调 | 学生报名操作细节 |

### 3.2 阶段 × 视角矩阵

| 阶段 | 学生 | 导师 | 培养单位 | 赛区/承办 | 典型通知 |
|---|---|---|---|---|---|
| 报名 | ● | ● | ○ | — | 报名开启/截止、赛题发布、章程 |
| 资格审查 | ○ | — | ● | — | 资格审核、材料补交 |
| 缴费 | ○ | ○ | ● | — | 报名费、会务费、对账 |
| 提交作品 | ● | ● | — | — | 作品上传、材料提交截止 |
| 评审 | ● | ● | ○ | — | 初审、答辩、复核 |
| 决赛 | ● | ● | ○ | ○ | 决赛日程、报到、颁奖 |
| 公示 | ● | ● | ● | — | 名单公示、成绩公布 |
| 获奖 | ● | ● | ● | — | 获奖名单、证书下载 |
| 报销 | ● | ● | ● | — | 报销文件、发票、票据 |
| 承办 | — | — | ● | ● | 承办征集、申办、组委会 |
| 动态 | ● | ● | — | — | 倒计时、开幕/落幕、企业合作 |

> ● 主要关注　○ 次要关注　— 默认不推送

### 3.3 通知分层

| 层级 | 触发条件 | 送达方式 | 频率 |
|---|---|---|---|
| 紧急快报 | AI `critical`，或规则识别「7 天内截止」且阶段属于报名/提交/缴费/资格审查 | 立即发信，不进摘要池 | 事件驱动 |
| 日程提醒 | 官方赛程的截止日命中 T-30 / T-7 / T-3 / T-1 | 独立一封「日程提醒」 | 每档一次 |
| 新通知 | 列表页出现新条目 / 官网修订同一篇 | 即时或进摘要池 | 每 10 分钟探测 |
| 日报 / 周报 | 用户选择 daily / weekly | 每天 08:00 / 周一 08:00 汇总 | 固定 |
| 归档 / RSS / 日历 | 全部公开通知 + 官方赛程 | 网页订阅 | 实时同步 |

### 3.4 降噪规则

1. **倒计时折叠**：标题含「倒计时 / 圆满 / 落幕 / 回顾 / 花絮」→ `stage=动态`、`is_low_value=true`，
   摘要邮件里折叠成一行，不进紧急通道。
2. **同标题去重**：同一内容同时出现在「大赛通知」和「大赛文件」时按标题去重，保留附件更全的一条。
3. **历史条目拦截**：超过 `push_max_age_days`（默认 60 天）的「新条目」只归档、不推送，
   避免首次接入赛事专区时把上年度名单当新闻群发。
4. **同天截止合并**：报名与提交同一天截止时，只发一条「报名截止」提醒。
5. **追赶模式**：单轮新增超过 `catchup_threshold`（默认 10）条时，只推最近
   `catchup_size`（默认 8）条，其余静默归档——仍能在归档页 / 日历看到，
   但不会连发多封大邮件。扩充数据源或长时间停摆后尤其重要。
6. **人员视角过滤**：收件人配置了 `audiences` 时，只收命中视角的通知；未配置则收全量。

### 3.5 后台设置（订阅者视角）

控制台 `/` 分为五块，改动即时保存到 `/api/prefs`：

1. **我的角色**：学生 / 导师 / 培养单位 / 赛区承办，多选按并集；
2. **关注的赛事**：20 项赛事复选（含 EDA 专项），提供「只选研电赛 / 全选 / 清空」；
   一个都不选 = 接收全部赛事；
3. **通知栏目**：报名参赛 / 评审与名单 / 决赛与收官 / 赛事动态；
4. **推送频率**：即时 / 日报 / 周报；
5. **暂停订阅**：暂停到指定日期。

筛选逻辑是三层交集：**栏目 × 角色 × 赛事**。全站级通知（赛程一览等）赛事为空，
不会被赛事筛选误伤。

### 3.6 角色版邮件

- 订阅者只勾选**一个角色** → 发该角色专版：
  - 主题前缀 `〔参赛学生〕`；
  - 顶部「按赛事汇总」：每项赛事的条数、最近时间节点、**该赛事的日历 / 列表链接**；
  - 正文按赛事分组，每组标题右侧带「赛事日历 / 赛事列表」。
- 勾选**多个角色** → 发综合版：保留「不同角色 · 各自要做的事」分区，
  同时也有「按赛事汇总」。
- 赛事链接形如 `/calendar.ics?email=…&token=…&contest=电子设计竞赛&audience=student` 与
  `/archive?contest=电子设计竞赛`，订阅者可以只订自己关注的赛事日历。
  日历链接必须带签名，公共日历已下线（无签名返回 401）。



## 四、邮件结构（读者实际看到什么）

综合版邮件从上到下：

1. **不同角色 · 各自要做的事**：学生 / 导师 / 培养单位 / 赛区四栏，
   每条给出「阶段 + 标题 + 要做什么」，最多 3 条。
2. **按赛事汇总**：每项赛事的条数、最近节点、赛事日历 / 列表链接。
3. **按分类分组的通知卡片**：日期、阶段徽标、赛事名、面向人群、AI 摘要、
   「要做什么」高亮条、事件日期、附件。
4. **退订 / 项目主页 / 研电赛官网**。

视角专用版（配置了 `personas[].mail_to`）：
标题下标注「本版面向：参赛学生」，只包含命中该视角的通知。

## 五、配置

```yaml
# config.yaml
max_age_days: 540          # 超过该天数的「新条目」只归档不推送
notices_limit: 200

schedule:
  enabled: true
  refresh_days: 7          # 赛程表每周最多刷新一次
  horizons: [30, 7, 3, 1]  # 截止前第 N 天提醒
  include:
    - 电子设计竞赛          # 只为该赛事生成提醒，避免 19 项赛事刷屏

personas:
  - key: student
    name: 参赛学生
    mail_to: ""            # 留空 = 跟随 MAIL_TO；填了则额外单独发一版
  - key: advisor
    name: 指导教师
    mail_to: ""
  - key: admin
    name: 培养单位
    mail_to: ""
  - key: organizer
    name: 分赛区 / 承办方
    mail_to: ""
```

新增赛事专区抓取（以创"芯"大赛 id=10 为例）：

```yaml
sources:
  - key: cpipc
    contest: 10            # 10 = 创"芯"大赛，6 = 电子设计竞赛
    max_pages: 2
```

## 六、AI 开启后的增强（提示词 v2）

| 能力 | 规则降级（无 Key） | AI 增强（有 Key） |
|---|---|---|
| 赛事名 | 标题别名匹配，识别不出默认研电赛 | 语义判断，含多项赛事时留空 |
| 阶段 | 关键词表 + 回顾类前置判定 | 结合正文判断，处理「延期」「补充通知」等隐含阶段 |
| 人群 | 阶段映射 + 标题点名（培养单位/导师/赛区） | 结合正文判断真实受众 |
| 要做什么 | 阶段模板句 | 结合截止日与材料要求生成具体动作 |
| 事件日期 | 双向窗口正则 + 合理性校验 | 语义抽取，支持「报到」「公示期」「证书申领」等 |
| 紧急度 | 7 天内截止 + 延期关键词 | 综合判断变更、影响面 |

AI 结果按内容指纹缓存在 `data/ai.json`，无新内容时零调用；
提示词升版（`prompts/manifest.yaml`）会让缓存全量失效并重算。

## 七、抓取压力与日历个性化

### 抓取：快，但不给官网加压

单轮要访问 13 个列表页 + 若干详情页。优化前后实测（同一网络、同一数据源）：

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 单轮耗时 | 37.6s | 15.3s |
| HTTP 请求数 | 40 次 | 26 次 |
| 同 URL 重复请求 | 14 次 | 0（进程内合并） |
| 单主机并发 | 1（串行） | ≤ 2（信号量） |

做法：

1. **两阶段抓取**：先只抓列表页判断有无变化，命中才抓详情——这是最大的省流手段。
2. **线程池并发**：列表页与详情页并行，`YDS_WORKERS` 默认 6。
3. **同 URL single-flight**：研电赛专区与专区轮询会命中同一个列表页地址，
   同一轮只真正请求一次，其余线程等待复用。
4. **每主机信号量**：`cpipc.acge.org.cn` 最多 2 个在途请求；专区默认每轮 4 项轮询。
5. **每日详情抽检限额**：`full_check_limit: 30`，只为最近 30 条已读通知复核正文。
6. **每日全量扫一遍专区**（`sweep_days: 1`）：轮询要靠 5 轮才覆盖 19 项，
   而 GitHub 的 `*/10` 定时任务会被节流（实测常是 2–5 小时才跑一次），
   只靠轮询归档会长期缺赛事。现在每天第一次运行强制扫全部 19 个专区，
   一次补齐归档（19 个列表页 ≈ 27 次请求，15 秒内完成）。

日志会输出 `HTTP 请求 N 次（同 URL 复用 M 次，重试 X 次，失败 Y 次）`，异常可直接定位。

### 日历：只对本人签发（公共日历已下线）

`/calendar.ics` **不再提供公开订阅**，只认签名链接：

```
https://<域名>/calendar.ics?email=you@example.com&token=<exp>.<sig>
```

- 没有签名、签名不对、token 过期、用途不符 → 一律 `401`，页面提示去控制台领取；
- 签名域是 `cal`，与退订的 `unsub` 互不通用；日历链接泄漏也无法退订；
- Worker 校验签名 → 读该用户 KV 里的偏好 → 只输出**其关注赛事 × 其角色**的事件；
  全站级通知（无赛事归属）不会被赛事筛选误伤；
- 赛程事件按赛事收敛，角色不影响赛程（赛程本身没有角色属性）；
- 控制台「我的日历」可一键复制地址；邮件页脚也有同一个入口；
- 响应头是 `Cache-Control: private, max-age=300` + `X-Robots-Tag: noindex`，
  不允许中间代理共享缓存，避免日程串人。

### KV 压力与优化

日历从「一份公开数据」变成「按人渲染」，必然要多读一次偏好；同时发现一个原有浪费：
通知与赛程存在同一条记录里，但 `loadNotices` / `loadSchedule` 各读了一次。

| 请求 | 改造前 | 现在（冷） | 现在（60s 内） |
|---|---|---|---|
| `/calendar.ics`（个人） | 3 次 | 2 次 | 1 次 |
| `/archive`、`/feed.xml` | 1 次 | 1 次 | 0 次 |
| 无签名日历 | — | 0 次（直接 401，不读 KV） | 0 次 |

做法：合并成一次读取 + isolate 内 60 秒缓存（写入时主动失效）+ KV `cacheTtl: 60`。
免费额度是每天 10 万次读，按每 15 分钟轮询估算：

| 日历订阅人数 | 每天轮询次数 | 每天 KV 读（按冷 2 / 热 1 估） |
|---|---|---|
| 3（当前） | 288 | < 600 |
| 100 | 9,600 | ~14,000 |
| 500 | 48,000 | ~70,000（仍在免费额度内） |

再往上就要换策略（按收益排序）：

1. **把偏好内嵌进签名 token**：日历请求 0 次 KV 读，代价是改设置后要等下一封邮件
   或下次进控制台才生效（链接在邮件与控制台都会重新签发）。
2. **Cache API 缓存整包响应**：按完整 URL（含 token）缓存 5 分钟，
   连 JSON 解析都省掉；缺点是改偏好后最多 5 分钟才生效。
3. 换 Workers 付费计划（$5/月，KV 读不限量）。

写压力没有变化：偏好保存仍是 1 次写，通知同步由内容指纹控制，只有真的变了才写。

## 八、效果预期

以 2026 年研电赛为例：

| 时间 | 改造前 | 改造后 |
|---|---|---|
| 4 月报名期 | 只在官网发通知时推一次 | 报名开始 + T-30/7/3/1 提醒，共 5 次节点提醒 |
| 6 月截止 | 依赖通知正文是否被抓到 | 赛程表直接给出 6 月 20 日，稳定提醒 |
| 8 月决赛 | 决赛通知 + 倒计时 8 条 | 决赛通知 + 决赛日程 + 报到提醒，倒计时折叠 |
| 9 月报销 | 报销文件一条 | 报销文件 + 发票时限提醒 |
| 全年 | 约 20 条，其中 14 条噪音 | 约 20 条精选 + 57 个赛程节点，噪音折叠 |

## 九、后续可扩展

1. **多赛事专区**：为创"芯"、AI、机器人配置 `contest` id，按需开启。
2. **分赛区资讯**：解析「分赛区资讯发布页」里的赛区链接，按学校所属赛区过滤。
3. **校内通知**：增加可配置的校级研究生院栏目（各校 DOM 不同，建议做成独立适配器）。
4. **周报导语**：启用 `prompts/digest/` 生成「本周三件事」。
5. **条件请求**：给列表页加 `ETag` / `If-Modified-Since`，304 时省掉传输体积。
