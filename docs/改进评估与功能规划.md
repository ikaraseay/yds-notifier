## 摘要

项目已完整上线：自定义域名 `notice.example.com` 可用，Worker / GitHub Actions / Resend 三端打通，安全加固与孟菲斯主题统一已完成。因此本次评估**不再重复讨论鉴权、CSRF、退订签名等已修问题**。

一句话结论：**当前最大风险不是安全，而是"静默失败"；最值得补的功能不是加推送渠道，而是"内容变更检测 + 截止日期/日历 + 历史归档"。**

- 有 4 条路径会让系统「看起来全绿、实际什么都没发生」：发信失败仍标记已推送、状态提交失败被吞掉、自测恒返回 0、官网改版后抓取 0 条被当成「无新公告」。这四个叠加，会让订阅者连续数周收不到通知而无人察觉。
- 去重只按文章 ID，**官网对同一篇文章发出「更正 / 补充 / 延长报名截止」时 100% 漏发**，而这恰恰是竞赛通知里最不能错过的信息。
- 送达率基线还差一步：`_dmarc.example.com` 实测**无记录**，Google 自 2025-11 起已对不合规流量做临时/永久拒收。
- 规模上，当前 2 位订阅者远未触顶，但按 10 分钟一轮的设计，订阅量到约 100 人就会先撞 KV 日读配额与 Resend 日发信额度（详见第三节）。

> **实现状态（2026-11-05 更新）**：本报告 A1 ~ A7 已全部落地；P0-1 / P0-2 / P0-3 / P0-4 / P0-7
> 与「/api/list 去 N+1」已一并修复，P0-5 补了 Actions 告警与心跳（Cloudflare 5xx 告警仍需面板配置）。
> **仍未处理**：P0-6 的 DMARC（需 DNS 操作）、P0-8 的魔法链接 nonce 原子消费。
> 具体改动见 README 与提交记录；仍需人工完成的是 DMARC 记录、Resend Webhook 签名密钥、
> 外部心跳 / 告警地址，以及 preview 环境与依赖锁定等 P2 项。

## 二、必须先修：会让通知「静默丢失」的问题（P0）

### P0-1 发信失败仍无条件写入「已推送」，通知永久丢失

- **证据**：`yds/main.py:267` 的 `state.mark(batch)` 位于收件人循环**之外**；`yds/main.py:265-266` 把失败邮箱记进 `failed`，但 `:273` 仍 `return 0`。`.github/workflows/notify.yml:96` 用 `if: always()` 把这份状态提交回仓库。
- **后果**：Resend 4xx、网络抖动、免费额度耗尽时，该批通知被写入 `seen.json`，下一轮 `State.has()` 判定已读，**永不重发**；Actions 全绿、无告警。README 中「状态回写失败时下轮会重发，宁可重复、不漏发」的描述与代码实际行为相反——真正危险的是**发信失败**而不是回写失败。
- **最小改法**：`state.mark(batch)` 只在该批所有收件人发送成功时执行；`if failed: return 1`；失败批次写 `data/pending.json` 供下轮重试；用 Resend `Idempotency-Key`（24 小时有效）兜住重试导致的重复。
- **验收**：本地把 `RESEND_API_KEY` 改成无效值触发一次，断言进程非零退出且 `seen.json` 无新增条目。

### P0-2 `git push` 重试耗尽后仍显示成功

- **证据**：`.github/workflows/notify.yml:111-115`，`git pull --rebase --autostash ... || true`，三次 push 全失败时循环最后执行的是 `sleep 5`，退出码 0。
- **后果**：状态没写回远端 → 下一轮**重复群发**同一批通知。与 P0-1 组合成「一个方向永久漏发、另一个方向重复群发」。
- **最小改法**：循环外加 `pushed=0` 标志，三次失败后 `echo "::error::..." && exit 1`；去掉 `|| true`。
- **验收**：把 remote 指向不可写地址跑一次提交步骤，断言 step 失败。

### P0-3 Python 自测恒返回 0，且没有真实单元测试

- **证据**：`yds/selftest.py:30` 的 `check()` 在 FAIL 时只 `print`，不累加失败；`main()` 末尾恒 `return 0`。仓库内无 pytest / unittest / conftest / fixtures。`.github/workflows/notify.yml:47` 把 `python -m yds.selftest` 当作门禁。
- **后果**：27 项自测只覆盖配置派生、签名格式、邮箱正则；**HTML 解析、状态读写、发信编排全部无测试**。此前 `yds/__main__.py` 未调用 `main()` 导致静默假成功，正是这类盲区的真实案例。
- **最小改法**：`check()` 累加 FAIL 并让 `main()` 返回 `1 if FAIL else 0`；补 2~3 份官网列表页 HTML fixture，用 pytest 断言 `parse_list` 条数 > 0 且字段完整；`notify.yml` 增加 pytest 步骤，`worker-ci.yml` 的 `paths` 补上 `yds/**`。
- **验收**：故意改坏一条断言，CI 必须变红。

### P0-4 官网改版 / 抓取全失败被伪装成「无新公告」

- **证据**：`yds/sources.py:94-101` 抓取异常或 `parse_list(html)` 返回空列表时直接 `break`；解析器硬编码 `#news_list`、`li.li`、`.day`、`.t2`、`ul.headlines-list li` 等选择器（`:129`、`:216`）；`yds/main.py:143-147` 只要 `pending` 为空就打印「无新公告，结束」并成功退出。两个 workflow 均无 `if: failure()` 告警。
- **后果**：官网一次改版即可让整套流程静默停摆数周，用户错过报名与截止节点。
- **最小改法**：本轮候选条目为 0 时视为异常（连续 N 轮 0 条才告警，计数器落 `data/`），`return 1`；补 HTML 快照契约测试；`notify.yml` 加 `if: failure()` 告警 job。
- **验收**：把 fixture 换成改版后的结构，断言 workflow 失败并产生告警。

### P0-5 无任何失败告警 / 心跳

- **证据**：`notify.yml` 与 `worker-ci.yml` 全文无 `if: failure()`；`worker/src/index.ts` 的 `console.error`、发信失败的 `log.error` 只进日志；`/health` 只返回 `ok`，且仅在 `scripts/ops.sh deploy` 后探测一次。
- **后果**：抓取失败、发信失败、Worker 500、Resend 拒绝、KV 超限都能静默持续数天。
- **最小改法**：Actions 失败 job 发 webhook 或 `gh issue create`；每轮成功末尾打一次 heartbeat（外部免费拨测服务，缺失即告警，可同时解决三、四节的 60 天自动禁用）；Cloudflare 配 5xx 错误率 Notification。
- **验收**：手工触发一次失败运行，10 分钟内收到告警。

### P0-6 DMARC 未落地，送达率基线不完整

- **证据**：实测 `dig +short TXT _dmarc.example.com` 为空；README 路线图里「DMARC 策略与送达率监控」仍未勾选。DKIM 与 Return-Path 子域 SPF 已有，Resend 域名验证已通过、实际发信成功。
- **依据**：Google 官方要求所有发件人做好 SPF/DKIM 并发布 DMARC（批量发件人最低 `p=none`），自 2025-11 起对不合规流量做临时/永久拒收；Outlook 自 2025-05 加入同类要求。Google 明确建议垃圾邮件投诉率低于 0.1%，硬上限 0.3%。一键退订必须是 `List-Unsubscribe` 中的 **HTTPS URL + RFC 8058 POST**，`mailto:` 和指向落地页都不算。
- **最小改法**：补 `TXT _dmarc` → `v=DMARC1; p=none; rua=mailto:dmarc@example.com`，观察 2~4 周后升 `p=quarantine`；注册 Google Postmaster Tools 看合规状态；**发一封真实邮件抓原始头**，确认 `List-Unsubscribe` / `List-Unsubscribe-Post` 确实被 Resend 带上了（Resend API 支持 `headers` 自定义头，但需实测，不能只信代码）。
- **验收**：Gmail「显示原始邮件」里 SPF/DKIM/DMARC 三项 PASS，且出现原生退订按钮。

### P0-7 公告「内容更新」被完全忽略

- **证据**：`yds/state.py:53` 的 `has()` 仅 `return notice.uid in self.data`；`mark()` 存了 `title/url/date` 却从不比较；`uid` 只来自 URL 中的文章 ID（`yds/models.py`）。
- **后果**：同一文章 ID 下改标题、补正文、加附件、发「更正/延长报名截止」，订阅者永远收不到。调研中多份竞赛通知都写明「后续调整、补充通知以官网发布为准」，这是高频场景。
- **最小改法**：对已见 UID 计算 `title + summary + 附件数` 的内容 hash 与 `seen.json` 比对，变化时按「【更新】」重推并高亮差异；`is_first_run` 改用显式 `version` 字段，避免状态文件损坏时误判首次运行而群发确认邮件。
- **验收**：改一份 fixture 的标题，断言产生一封「更新」邮件且状态 hash 被刷新。

### P0-8 魔法链接 nonce 的「一次性」在真实 KV 上不成立

- **证据**：`worker/src/handlers/login.ts:100-103` 用两次独立 KV 操作 `get` + `delete`；KV 最终一致且默认有边缘缓存（官方 `cacheTtl` 最小 30 秒），`delete` 不会立即使其它 PoP 失效。e2e 用的 `MockKV` 是同步无缓存内存实现，恰好掩盖了这个竞态。
- **后果**：并发双击或跨地域请求可能都读到有效 nonce，同一链接签发多个会话。
- **最小改法**：把 nonce 消费移入项目已有的 `RATE` Durable Object，用 `state.storage` 在同一实例内原子 `get`/`delete`；KV 无 CAS，DO 是正解。
- **验收**：并发 20 次请求同一链接，断言只有 1 次成功。

## 三、结构性风险与规模天花板（P1）

### 3.1 状态存在 git 仓库里，是多个问题的共同根因

`data/seen.json` 每次有新公告就产生一个 `[skip ci]` 提交（`state_keep: 800` 使文件长期约 150 KB）。`concurrency` 只约束本 workflow，人工 push、Workers Builds、另一个 workflow 不受约束；`State.save()` 的单机原子写跨机器无锁；`[skip ci]` 能否被 Cloudflare Workers Builds 跳过**未验证**，若不跳过，每次状态提交都会触发一次完整 Worker 构建。

更现实的风险是 **GitHub 的 60 天规则**：公开仓库若无提交活动，scheduled workflow 会被自动禁用且几乎无通知。本项目是 public 仓库，而状态提交只在「有新公告」时发生——赛事淡季连续两个月没有新公告，就既没有通知也没有提交，可能正好触发禁用。

**建议**：状态迁到 Cloudflare KV / R2（项目已有 KV 绑定）或 D1，彻底去掉 git 回写；配合 Queues 做异步化。这一项改造收益最大，但涉及状态迁移，建议排在 P0 之后作为专项。

### 3.2 免费额度的具体天花板（官方 2026 年数值）

| 平台 | 限制 | 本项目何时撞线 |
|---|---|---|
| Workers Free | 100,000 请求/天；每次调用 CPU 10 ms；外部 subrequest 50/请求（内部服务 1000/调用） | 请求量不是瓶颈；**CPU 10 ms 决定不能把 HTML 解析搬进 Worker** |
| Workers KV | 100,000 读/天、1,000 写/天；`cacheTtl` 最小 30 s | `/api/list` 对每个订阅者 `getUser`（`worker/src/handlers/api.ts:50`），每天 144 轮 × N 次读 → **N≈694 触顶**，加上其它接口实际更早 |
| Cron Triggers | 免费版每账户 5 个 | 若迁到 Worker 调度，1 个够用，但 CPU 10 ms 不够解析多个页面 |
| Queues | 2026-02 起免费版 10,000 操作/天，保留 24 小时 | 足够承载「状态写入 + 发信任务」异步化 |
| Turnstile | 免费 20 个 widget，验证次数无上限 | 可直接用于登录表单防刷 |
| Resend Free | 100 封/天、3,000 封/月、1 个 webhook、30 天数据保留 | 每人每批次 1 封 → **N 人 × B 批次 ≤ 100/天**；当前 2 人无压力，50 人 × 2 批次即到顶 |
| GitHub Actions | `*/10` = 144 次/天；public 仓库 60 天无活动禁用 schedule | 通知以天/周为单位，10 分钟轮询收益极低 |

其它同向优化：`MAX_CONFIRM_PER_DAY=200`（`worker/src/env.ts:125`）**大于 Resend 免费日额度 100**，光登录邮件理论上就能挤掉通知邮件；`day:` 是全局唯一 Durable Object key（`login.ts:48`），既是热点也可被打满造成全站无法登录；`senders.py:88-103` 有 3 次固定 3/6 秒重试但不读 `Retry-After`、无指数退避、无跨运行重试。

### 3.3 其它工程化缺口

- **发信编排**：逐人 POST，未用 Resend Batch API（100 封/次；注意任一封校验失败会整批失败、不支持附件与 `scheduled_at`）。
- **名单接口 N+1**：在 `sub:<email>` 的 value 里冗余 `prefs` 即可去掉 N 次 `getUser`，同时消除 `sub:` 与 `user:` 两次写入之间的 KV 一致性窗口；响应还应带 `truncated` 标志并支持 cursor 分页。
- **防刷与同意证据**：无 Turnstile、无 double opt-in，任意合法邮箱即可触发发信；首次点链接即自动订阅，consent 记录弱。
- **三条部署链路并存**：Workers Builds、`worker-ci.yml` 手动兜底、`ops.sh deploy` 都能 `wrangler deploy`，且 `sync-config` 会把本地 `.env` 的 KV id / 域名写回 `wrangler.toml`，本地一次误操作就能把生产指向别的 KV。建议生产只保留 Git 自动部署，其余改为 dry-run 或强制确认。
- **依赖与元数据**：`requirements.txt` 是范围版本、无 lock 文件、无 dependabot；无 `LICENSE` / `CONTRIBUTING.md` / `SECURITY.md` / issue 模板（README 已如实声明未指定许可证）；无 staging/preview 环境。

## 四、网上调研：需求信号与可复用能力

### 4.1 目标用户的真实痛点（赛事通知场景）

调研到的竞赛通知有几个稳定特征，直接决定功能优先级：

1. **信息分散、官方不主动通知**：通知散落在组委会官网、学校院系网站、微信公众号，多份通知明确写「各类信息不会通过已报名选手的邮箱或电话另行通知」「后续调整、补充通知以官网发布为准」。这正是订阅器存在的理由，也意味着**漏抓比误抓更不可接受**。
2. **核心价值是时间节点**：通知里最重要的是报名截止、赛程、缴费、材料提交时间，且**同一赛事不同赛项截止日期各不相同**（例：某校通知里四个赛项分别是 11/6、11/13、11/19、11/25 截止）。
3. **变更比新增更关键**：「更正 / 补充 / 延期 / 新增考点」类更新常在原页面或后续通知里发布，不做内容 diff 就抓不到。

学术会议领域已有成熟做法可直接借鉴：`conferences-computer.science` 提供 `deadlines.ics` / `events.ics` 日历订阅，支持按地区/等级筛选的多个 feed，强调**订阅而非导入**（延期时原地更新事件、不留重复），并把「截止时刻的时区问题」写进说明。这套模式搬到竞赛场景几乎不需要重新设计。

### 4.2 平台合规（官方口径）

- Google：自 2024-02 起，一天内向个人 Gmail 发 5,000 封以上算批量发件人，须验证身份、避免 unwanted mail、提供便捷退订；**自 2025-11 起加强执行，不合规邮件会被临时或永久拒收**。所有发件人（不论量级）都建议 SPF + DKIM + DMARC；From 域需与 SPF 或 DKIM 域对齐。
- 一键退订：必须在 `List-Unsubscribe` 里给 **HTTPS URL** 且按 RFC 8058 支持 POST；`mailto:` 不符合，指向落地页/偏好页也不符合；退订须在 2 天内生效。本项目 Worker 的 POST 分支语义正确，但**需抓真实邮件原始头确认 Resend 未剥离**。
- 投诉率：Google 建议低于 0.1%，硬上限 0.3%；可用 Postmaster Tools 的合规状态面板监控。Microsoft 自 2025-05 对 Outlook.com 加入同类要求。
- 低量发件人也应照做：域名声誉一旦受损，恢复需要数周低量高互动发送。

### 4.3 同类产品功能对标

| 参照 | 值得借鉴的能力 |
|---|---|
| `changedetection.io`（约 34k stars，Apache-2.0） | 按词/行/字符的内容 diff、历史快照、只监控页面局部、80+ 通知渠道、**基于变更生成 RSS feed**、可选 LLM 过滤与摘要 |
| `Huginn` | 规则化条件判断、峰谷检测与**定时聚合摘要**、把事件再发布成 RSS / JSON 供其它系统消费 |
| 主流 newsletter 实践 | double opt-in + 确认/欢迎邮件、记录 consent 时间与来源、偏好中心含**频率与暂停**、**公开归档页**、bounce/complaint 自动清理、退订原因分析 |
| 学术会议日历 | `.ics` 订阅 feed、按维度筛选、变更时原地更新事件 |

对照下来，本项目已有「按栏目偏好 + 邮件 + 一键退订 + 注销」，**缺的集中在：内容变更、时间结构化、归档/再发布、频率控制、确认与欢迎、回执闭环**。

### 4.4 平台已提供、可低成本复用的能力

- **Cloudflare**：Queues（2026-02 进入免费版，10,000 操作/天）可做发信异步与重试；Turnstile 免费且验证次数不限；D1 / R2 可替代 git 存状态；Email Routing 可接回信；Workers Logs / Analytics Engine 可做错误统计；Cron Trigger 免费 5 个/账户。
- **Resend**：Batch API（100 封/次）、`Idempotency-Key`（24 小时，防重复群发）、Webhook 事件（`email.bounced` / `email.complained` / `email.failed` / `suppression.added`）、**自动 suppression list 免费版就有**；Free 版含 1 个 webhook endpoint，足够接一个 Worker 路由。
- 结论：**不需要新增付费服务**就能补齐可靠性闭环；升配的触发点应该是订阅量（Resend Free 100 封/天），而不是为了换架构。

## 五、功能建议清单（按性价比排序）

### A. 高价值、低成本，建议先做

| # | 功能 | 为什么（依据） | 最小实现 | 验收 |
|---|---|---|---|---|
| A1 | **内容变更检测与「【更新】」重推** | 4.1 的「更正/延期」高频；P0-7 目前 100% 漏发 | 已见 UID 存内容 hash，变化时 diff 标题/附件并重推 | 改 fixture 标题能产出一封更新邮件 |
| A2 | **截止日期结构化 + `.ics` 日历订阅** | 4.1 的多截止日期；学术会议已验证的订阅模式 | 从标题/正文抽日期 → `/calendar.ics`（可按栏目出多个 feed），事件 UID 稳定、延期时原地更新；邮件里附「加入日历」 | Apple/Google 日历订阅后能看到截止日，延期只更新不重复 |
| A3 | **公开归档页 `/archive` + `/feed.xml`（RSS/Atom）** | 4.3 的 newsletter 归档与 changedetection.io / Huginn 的再发布 | 把 `seen.json` 的 title/url/date 渲染成静态页与 feed，按栏目过滤 | 错过邮件也能查到；RSS 阅读器可订阅 |
| A4 | **频率与暂停控制** | 4.3 偏好中心通行做法；10 分钟轮询下易打扰 | prefs 增加 `frequency: instant / daily / weekly` 与 `paused_until`，发信前按频率聚合 | 选「周报」的用户一周只收 1 封 |
| A5 | **确认/欢迎邮件 + double opt-in** | 4.2 Google 要求「确保收件者已明确选择接收」；降低 hard bounce、留存 consent 证据 | 订阅状态加 `pending`，确认邮件点后才置 `confirmed`；记录时间与来源 | 未确认邮箱不进 `/api/list` |
| A6 | **失败告警 + heartbeat + Resend webhook 闭环** | P0-5；4.2 的投诉率与送达率 | Actions `if: failure()` + 外部心跳；Worker 加 `/webhooks/resend` 验签后处理 `bounced/complained/suppression.added`，自动移出名单 | 发到 `bounced@resend.dev` 后该地址被自动摘除；断跑 30 分钟内告警 |
| A7 | **退订时提供「改为低频」+ 原因收集** | 4.3 退订分析；README 路线图已有「退订原因统计」待办 | 确认页加单选原因与「改成周报」按钮，写入 KV 供统计 | 退订率与原因可在 `/api/stats`（鉴权）查看 |

### B. 中成本，随版本迭代

| # | 功能 | 要点 |
|---|---|---|
| B1 | **状态迁出 git → KV / D1 + Queues 异步发信** | 一次性消除并发冲突、仓库膨胀、`[skip ci]` 不确定性、60 天禁用风险；配合 A6 的重试队列 |
| B2 | **Turnstile + 登录邮件额度收敛** | 表单加 Turnstile；`day:` 按 hash 分片避免单点 DoS；`MAX_CONFIRM_PER_DAY` 降到 ≤ 100 并给通知邮件留余量 |
| B3 | **数据源插件化 + 契约测试 + 多源扩展** | 选择器外置到 `config.yaml`，每个源配 HTML fixture；README 路线图的「更多官方渠道」可借此落地；新增学校院系站、公众号镜像源 |
| B4 | **关键词订阅 / 重要性分级** | prefs 增加关键词（标题正则），命中「报名截止 / 延期 / 名单公示」的可标为高优先级即时推送 |
| B5 | **工程化补齐** | `requirements.lock` + dependabot；`LICENSE` / `CONTRIBUTING.md` / `SECURITY.md` / issue 模板；`[env.staging]` + 独立 KV 的预览环境；部署链路收敛到 Git 单一路径 |

### C. 需评估后再决定（有明确取舍）

| # | 方向 | 取舍 |
|---|---|---|
| C1 | **把抓取整体迁到 Cloudflare Cron** | 技术可行且日常请求量远低于免费额度，但 Workers Free **每次调用仅 10 ms CPU**，解析多个 HTML 页几乎必然超限，需 Workers Paid（$5/月起）；BeautifulSoup 要重写成 TS + HTMLRewriter，Cron 无自动重试与失败告警。建议**只迁状态与调度，不迁解析**；当前「Actions 抓取 + Worker 订阅」零成本且更稳 |
| C2 | **多渠道推送**（Telegram / 飞书 / 企业微信 / 通用 Webhook） | 4.3 显示是同类产品标配，但国内渠道可用性与合规需逐个评估；建议先做「通用 Webhook + Telegram」两个出口，架构上把「发送」抽象成 adapter |
| C3 | **LLM 摘要与降噪** | Workers AI 有免费额度；对「长通知提炼要点 + 判断是否重要」有用，但会带来延迟、成本与误判风险，建议先做规则版（关键词 + 长度截断）验证价值 |
| C4 | **数据导出、i18n、深色模式、多赛事支持** | 有价值但当前 2 位订阅者阶段优先级低；其中「数据导出」若涉及合规要求可提前 |

### 明确不建议做

- **进一步提高轮询频率**：`*/10` 已远超「通知以天/周为单位」的实际需求，反而是 KV 读配额、Actions 额度与 Resend 额度的主要消耗来源；建议改 `*/30` 或按赛事周期动态调度。
- **为省掉一个 GitHub Actions 而全量迁移到 Worker**：见 C1，成本与稳定性都不划算。
- **加打开/点击追踪像素**：隐私代价高，且对事务类邮件反而可能损害送达率；用 Resend 的 delivered / complained 事件已足够。
- **在订阅量很小时升 Resend Pro（$20/月）**：先把 Batch API、频率控制、去重做好，触顶再升。

## 六、分期路线图与验收

| 阶段 | 内容 | 完成标准 |
|---|---|---|
| **P0（先修可靠性）** | P0-1 ~ P0-8 | 故意制造发信失败 / 状态 push 失败 / 官网改版 / 并发点链接四类故障，系统都能**失败可见、可重试、不丢不重**；DMARC 三项 PASS 且原始头含一键退订 |
| **P1（补产品闭环）** | A1 ~ A7 | 订阅者能：看到内容更新、把截止日加入日历、查历史归档、选周报、退订时改低频；运营能：收到失败告警、看到退订原因、bounce 自动清理 |
| **P2（平台化）** | B1 ~ B5 | 状态不再产生 git 提交；订阅量 100+ 时仍在免费额度内；Python 与 Worker 都有真实测试门禁；生产只有一个部署入口 |
| **P3（按需）** | C1 ~ C4 | 有明确用户反馈或规模触发后再评估 |

建议的先后顺序：**P0-1/2/3/4/5 → P0-7（更新检测）→ A2/A3（日历与归档）→ A6（告警闭环）→ B1（状态迁移）**。前四项都是几行到几十行改动，却决定了「这个项目可不可信」。

## 七、需要你在线上确认的 5 件事

代码与公开文档无法判定，建议核验后再定最终优先级：

1. `_dmarc.example.com` 是否真的未配置（本次 `dig` 为空），以及 Resend 域名面板显示的状态。
2. 真实邮件的原始头里是否带 `List-Unsubscribe` / `List-Unsubscribe-Post`（Resend 支持 `headers` 字段，但需实测未被剥离或覆写）。
3. Workers Builds 是否跳过 `[skip ci]` 状态提交（影响 B1 的紧迫性）。
4. Cloudflare 账户当前是 Free 还是 Paid（决定 CPU 10 ms 与 KV 日配额是否适用）。
5. 仓库 scheduled workflow 是否曾被 60 天规则禁用过，以及淡季是否有其它提交活动。
